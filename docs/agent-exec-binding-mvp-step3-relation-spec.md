# Step 3 — Halo2 约束关系草案（v0.1）

状态：设计草案，尚未实现 Halo2 电路；不改变现有 Ed25519 / SHA-256 基线。

## 1. 本轮数据访问基线验收

Windows 本机复现结果：48/48 tests PASS；三步演示均 accepted；实际返回行数为 2、2、1，总计 5；计划预留上限为 2+2+1=5。演示使用合成内存数据，不访问真实数据库。

注意：Step 0 与 Step 2 都返回了 `sales_records` 中的 north 记录。因此 5 表示跨调用累计返回的行事件数，不是 5 条不同记录，也不是 5 个不同主体。当前配额语义是“预留最大返回行数的总和”，重复查询按调用重复计数。

## 2. v1 只证明什么

第一版 Halo2 电路只处理一个清晰子问题：

> 给定一份有序、有限的工具调用计划，证明每一步预留行数不超过隐藏的单步上限 L，且所有步骤的预留行数之和不超过隐藏总配额 B；同时证明这些动作确实组成公开的计划承诺根 R_plan。

v1 不在电路内证明字段/资源/filter allowlist。它们暂时仍由现有授权方的确定性策略检查处理。这样可以先独立测量“计划级隐藏配额证明”的正确性和成本，再扩展到完整策略谓词。

## 3. 数学对象

计划为有序动作序列：

\[
A=(a_0,a_1,\ldots,a_{n-1}),\qquad 1\le n\le 16.
\]

每个动作至少包含：

\[
a_i=(i,\operatorname{resource}_i,\operatorname{filters}_i,
\operatorname{fields}_i,m_i),
\]

其中 \(m_i\) 是该步骤预留的最大返回行数，不是实际返回行数。

隐藏配额策略：

\[
P_q=(B,L),
\]

其中 B 为整份计划的累计预留行数上限，L 为单步预留行数上限。

## 4. 公共输入与私有见证

### 公共输入（公开声明）

- \(C_q\)：隐藏配额策略的承诺；
- \(R_{plan}\)：有序动作计划的 Poseidon Merkle 根；
- \(n\)：动作数量；
- \(H_{ctx}\)：主体、租户、会话等上下文摘要；
- \(H_{schema}\)：工具 schema 摘要。

freshness（plan nonce、签发时间、过期时间）由外层签名授权信封绑定；执行端还必须对每个步骤维护一次性 nullifier。若后续证明验证接口要求把 nonce 纳入公共输入，可在接口冻结前加入，不能在实现后悄悄变更。

### 私有见证

- B、L；
- 配额承诺盲化随机数 r；
- 有序动作序列 A；
- 为计算计划根所需的中间哈希见证（也可以在电路内直接计算）。

## 5. v1 约束关系

电路验证以下关系：

1. **配额承诺一致：**
   \[
   C_q=\operatorname{Poseidon}(\texttt{quota-v1},B,L,r).
   \]
2. **动作数合法：**
   \[
   1\le n\le16.
   \]
3. **计划根绑定：**按固定编码对每个动作计算叶哈希，并按固定深度、域分离和规范 padding 规则构造 Merkle 根，要求等于公共输入 \(R_{plan}\)。叶子必须包含 step index 与 \(m_i\)，防止重排或修改预留额度。
4. **步骤连续：**有效叶子的 step index 恰为 \(0,1,\ldots,n-1\)，无缺口；非活动槽位使用唯一规范 padding。
5. **单步范围与上限：**
   \[
   1\le m_i<2^{16},\qquad m_i\le L.
   \]
6. **累计预留额度：**
   \[
   S=\sum_{i=0}^{n-1}m_i,\qquad S\le B.
   \]
7. **整数范围：**B 使用 32-bit range check；L 和每个 m_i 使用 16-bit range check；由于最多 16 步且每步最多 65535，S 最大为 1,048,560，小于 \(2^{20}\)，因此 S 可用 20-bit range check。比较必须按整数语义实现，不能只依赖有限域中的大小关系。
8. \(H_{ctx}\) 与 \(H_{schema}\) 作为公共输入进入证明声明，并由外层授权信封签名绑定；执行网关必须检查本地上下文和工具 schema 摘要与之相同。

## 6. 计划执行侧的验证

计划证明通过后，执行网关逐步验证：

- 当前动作和 inclusion path 对应同一个 \(R_{plan}\)；
- 该动作的 step index 是下一步；
- 每步 nullifier 只消费一次；
- 工具实际返回行数不超过动作中的 \(m_i\)；
- 工具签名回执绑定 grant、计划根、动作摘要、结果摘要、上下文和 schema。

v1 仍然信任工具端正确执行查询并诚实签署回执。签名回执不是数据库结果真实性证明。

## 7. 电路编码约束

不要在 Halo2 电路里直接处理任意长度字符串或 Python 字典。先把当前固定 demo schema 映射成稳定整数 ID：

- resource ID；
- field ID；
- filter-field ID；
- filter-value ID。

动作采用固定最大槽位编码，未使用槽位必须 canonical padding。动作叶哈希与 Merkle 树哈希使用电路友好的 Poseidon，并明确域分离。它与现有 Python 基线中的 SHA-256 Merkle root 不同，必须升级协议版本（例如 `data-query-v2-poseidon`），不能声称两者根值兼容。

## 8. 明确不声称的性质

- 不证明数据库内容真实、完整、最新或来源可信；
- 不证明查询结果没有被工具端伪造；
- 不提供 differential privacy，也不抵抗跨查询推断；
- 不隐藏 Agent 向工具发送的动作参数；
- v1 不在 ZK 电路中证明资源、字段、filter allowlist；
- 不把预留行数总和解释为唯一记录数或唯一用户数；
- 不宣称已具备跨电路泛化或学术创新性。

## 9. 下一步编码前的验收项

在写 Halo2 代码前，需要先冻结：

1. v1 是否只证明 B/L 配额关系（建议是）；
2. 动作最大数量固定为 16；
3. 单步行数 16-bit、B 32-bit、累计和 20-bit；
4. 动作字段 ID 和 canonical encoding；
5. Poseidon 参数、域分离常量、Merkle padding 规则；
6. 公共输入顺序与 proof/grant/nonce 的绑定方式；
7. 至少覆盖边界值、超限、重排、篡改、padding 和整数溢出的测试向量。

在这些项确认前，不开始实现电路，避免后续因编码或语义变化推倒重来。
